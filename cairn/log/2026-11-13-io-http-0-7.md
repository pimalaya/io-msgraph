# io-http 0.7

The crate moves from io-http 0.6 to 0.7, and its dev-dependency io-oauth from 0.5 to 0.6 (the live suite mints its app-only token through the client credentials flow, whose call compiles unchanged). One io-http remains in the graph. Nothing in src or tests stopped compiling, and no test pinned the old reading of headers or bodies. Trivial change, landed without a proposal.

**Requests that split.** io-http 0.7 refuses a method or a header name that is not a token and a header value holding a CR, a LF or a NUL, at the first resume of `Http11Send`, before any write. `From<Http11SendError>` now reads that refusal as `MsgraphSendError::InvalidRequest`, not as `Send`: no exchange took place and the stream is untouched, which a caller dropping its connection on a `Send` error has to be able to tell. The reason names the header, never its value. The JSON send and the two raw `$value` sends share the conversion. Test `a_token_holding_a_line_break_never_reaches_the_wire`, which showed the `Send` variant ("Microsoft Graph HTTP request failed: HTTP/1.1 send failed: HTTP serialize request failed: invalid value for header Authorization") before the conversion. That io-http 0.6 wrote such a token is read from the 0.7.0 changelog, not run here.

**Path segments** (family audit of 2026-11-13, FAM-11). `path_segment` keeps its signature and now encodes through `rfc3986::path::http_url_build` of io-http, reading the segment back from the URL it builds on `MSGRAPH_API_BASE`; the local encoder is gone. The 63 files that build a path still compose a path with `format!` and join it, since the helper takes whole segments and `user_path` answers one or two: moving them is a rewrite of every constructor, left out of a dependency bump. Compared byte by byte over ASCII before the swap, the two encoders differ on seven bytes and nowhere else:

- a tab, a CR or a LF was sent as `%09`, `%0D` or `%0A` and is now refused with `InvalidRequest`;
- `[`, `]`, `^` and `|` were sent encoded and are now sent as they are (the URL parser's path set, not the RFC 3986 `pchar` set).

No test pinned either, and a Graph id (base64url) holds none of them. A user principal name may hold a `^`: whether Graph reads it raw in a path was not checked live. Test `a_path_segment_refuses_what_url_resolution_drops` gained a tab and a line break; `a_path_segment_keeps_a_graph_id_and_encodes_separators` passes unchanged.

Capabilities moved: request-paths (one requirement modified), errors (one added).
